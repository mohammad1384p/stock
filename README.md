# stock — ربات سفارش زمان‌دار Exir

در ساعت مشخص (ساعت:دقیقه:ثانیه) شروع به ارسال درخواست ثبت سفارش به
`https://khobregan.exirbroker.com/api/v1/order` می‌کند و **۱۰ ثانیه** با فاصله‌ی
**۳۰۵ میلی‌ثانیه** (≈ ۳۳ درخواست) ادامه می‌دهد. پاسخ هر درخواست در ترمینال چاپ می‌شود.

همین ربات یک **وب‌پنل** هم دارد (`web_panel.py`) که با آن می‌توانید از مرورگر سفارش را فرم
کنید، لاگین/کپچا را انجام دهید و پاسخ‌ها را زنده ببینید — ببینید
[وب‌پنل (اختیاری)](#وب‌پنل-اختیاری--web_panelpy).

## نصب

روی دبیان/اوبونتو‌های جدید (پایتون ۳.۱۲ به بعد) نصب سراسری با `pip` خطای
`error: externally managed environment` (PEP 668) می‌دهد؛ یک محیط مجازی بسازید:

```bash
sudo apt install -y python3-venv      # فقط اگر venv روی سیستم نصب نیست
python3 -m venv .venv
source .venv/bin/activate             # ویندوز:  .venv\Scripts\activate
python -m pip install -r requirements.txt
```

از این پس ربات را با پایتون همین محیط اجرا کنید: بعد از فعال‌سازی، `python exir_bot.py ...`
کافی است و بدون فعال‌سازی باید `.venv/bin/python exir_bot.py ...` بنویسید.

- اگر دانلود از PyPI کند است یا نیمه‌کاره می‌ماند، پرچم‌های مقاوم را اضافه کنید:
  `python -m pip install --timeout 120 --retries 10 -r requirements.txt`
  (با `-i <آدرسِ آینه>` هم می‌توانید از یک mirror داخلی استفاده کنید.)
- راه دیگر بدون محیط مجازی: `pip install --break-system-packages -r requirements.txt`
  که در صورت تداخل با پکیج‌های سیستمی توصیه نمی‌شود.

### هدرها و نشست ورود
- هدرهای ثابت مرورگر (Accept، زبان، User-Agent، Origin، Referer و sec-*) روی نشست تنظیم می‌شوند؛ Referer هنگام ورود به صفحه‌ی login اشاره می‌کند و برای سفارش به market-view.
- مقدار `x-app-n` از `--app-n` یا `-H 'x-app-n: ...'` برای ورود و سفارش یکسان نگه داشته می‌شود. اگر ندهید، ربات یک مقدار **تولیدی** با همان شکلِ دیده‌شده در مرورگر (`<۱۳ رقم>.<۸ رقم>`، مثل `2018887747744.29964494`) می‌سازد و همان را در سفارش‌ها هم می‌فرستد؛ نسخه‌های قبلی `NaN.<عدد>` می‌ساختند که هیچ‌وقت در درخواست مرورگر دیده نشده بود. الگوریتم واقعی این هدر قابل تأیید نیست؛ تغییر هدرها تضمین رفع ۹۰۰۹ نیست.
- هدر `clientid` مثل درخواست ورودِ مرورگر روی **همه‌ی** درخواست‌ها (کپچا، ورود و سفارش) فرستاده می‌شود؛ مقدارش پیش‌فرض خالی است و با `--clientid` (یا `EXIR_CLIENTID`) قابل تغییر است. `--clientid off` این هدر را کاملاً حذف می‌کند. (نسخه‌های قبلی این هدر را فقط در درخواست ورود می‌فرستادند و سفارش‌ها بدون آن می‌رفتند.)
- کوکی‌های غیرمنقضیِ همان میزبان، همراه با دامنه، مسیر و انقضا، در فایل محلی توکن ذخیره و بازیابی می‌شوند. این فایل محرمانه است و نباید به اشتراک گذاشته شود. فایل‌های قدیمی همچنان خوانده می‌شوند؛ برای ذخیره‌ی نشست کامل یک بار `--login-only` اجرا کنید.
- اگر توکن فعال باشد، هدرهای نشست و کوکی‌های داخل `--body-file` جایگزین نشست فعلی نمی‌شوند. هدرهای دلخواه را پیش از ورود با `-H` یا `--app-n` تنظیم کنید.
- Host، Content-Length و Accept-Encoding را کتابخانه مدیریت می‌کند. مقادیر خصوصی Cookie و هدرهای رهگیری sentry/baggage نمونه در کد کپی نشده‌اند.

## اجرا
تعاملی (اگر توکن معتبر ذخیره نشده باشد اول لاگین می‌کند، بعد نماد، تعداد، قیمت و ساعت پرسیده می‌شود):
```bash
python exir_bot.py
```
با آرگومان:
```bash
python exir_bot.py -s IRO7TONP0001 -q 10 -p 6700 -t 08:44:59.700
python exir_bot.py -s وتوصا -q 10 -p 6700 -t 08:45:00 --app-n "2018887747744.29964494"
```

> برنامه‌های اجرایی پروژه: `exir_bot.py` (خط فرمان) و `web_panel.py` (وب‌پنل، بخش بعدی)؛
> ماژول‌های کمکی `exir_auth.py`، `timesync.py` و `captcha_web.py` هستند.
> ابزارهای عیب‌یابی: `probe_order.py` (پیدا کردن علت ۴۰۳/۹۰۰۹ با حذف فرضیه‌ها)،
> `compare_request.py` (مقایسه‌ی درخواست مرورگر با ربات) و `diagnose_session.py` (گزارش آفلاین نشست). آرگومان‌های
> `--host` / `--port` متعلق به `web_panel.py` است (نه `exir_bot.py`)؛ در `exir_bot.py`
> تنها وب‌سرور موجود، صفحه‌ی موقت کپچا با `--captcha-web [PORT]` است (پیش‌فرض `8765`).

## وب‌پنل (اختیاری) — `web_panel.py`
اگر می‌خواهید همه‌چیز از مرورگر انجام شود (فرم سفارش، لاگین/کپچا، شروع و توقف، لاگ زنده):

```bash
python web_panel.py                                    # پیش‌فرض: 0.0.0.0:2345
python web_panel.py --host 127.0.0.1                   # فقط روی خود سرور (پورت 2345)
python web_panel.py --port 2345 --time-sync off        # بدون همگام‌سازی ساعت (برای تست)
python web_panel.py --port 2345 --token "<JWT>" --app-n "2018887747744.29964494"
python web_panel.py --port 9000                        # اگر 2345 اشغال بود
```

آدرس چاپ‌شده در ترمینال را در مرورگر باز کنید؛ اگر سرور از راه دور است:
`ssh -L 2345:127.0.0.1:2345 user@server` و بعد `http://127.0.0.1:2345/`.

پنل همان موتور `exir_bot.py` را صدا می‌زند (`build_session`، `build_body`، `resolve_isin`،
`send_order`، `Stats`)، پس رفتار ارسال دقیقاً یکی است؛ فقط ورودی/خروجی از مرورگر می‌آید.

- **۱) مشخصات سفارش**: نماد/نام/ISIN (با پیشنهاد از `symbols.json`)، تعداد، قیمت، ساعت شروع
  (`HH:MM:SS.mmm`)، خرید/فروش، مدت (ثانیه)، فاصله (میلی‌ثانیه)، «توقف پس از اولین موفقیت»،
  «اجرای آزمایشی (dry-run)»، روش همگام‌سازی ساعت و (اختیاری) کادر «بدنه‌ی سفارشی» برای
  چسباندن JSON یا خروجی «Copy as fetch» مرورگر (همان `--body-file`).
- **دکمه‌ها**: «⏱ زمان‌بندی و شروع»، «⚡ شروع فوری (۳ ثانیه بعد)»، «⏹ توقف» (در حال انتظار هم
  کار می‌کند و هیچ درخواستی نمی‌فرستد)، «🔄 همگام‌سازی ساعت».
- **۲) ورود / توکن**: نام کاربری، رمز و OTP را در فرم بزنید؛ تصویر کپچا **با نشست همان سرور**
  گرفته و از داخل خود پنل نمایش داده می‌شود (پورت جدا لازم نیست) — کد را همان‌جا بفرستید.
  توکن در `.exir_token.json` ذخیره و تا انقضا استفاده می‌شود؛ دکمه‌ی پاک‌کردن توکن هم هست.
- **۳) وضعیت اجرا**: خلاصه‌ی سفارش (نماد→ISIN، ارزش کل، ساعت شروع، تعداد درخواست، ساعت مرجع،
  توکن) + شمارش معکوس تا شروع.
- **۴) پاسخ درخواست‌ها**: جدول زنده‌ی هر درخواست (شماره، ساعت ارسال، HTTP، توضیح خطا).
- **۵) لاگ زنده**: همان چاپِ ترمینال (خلاصه، بدنه‌ی هر پاسخ، راهنمای خطاهای ۹۰۰۹/۴۲۲ و گزارش نهایی).

نکته‌ها: هر بار فقط یک اجرا؛ تا پایان اجرا دکمه‌ها قفل می‌شوند. اجرای آزمایشی حتی بدون توکن کار
می‌کند (هدرها و بدنه را نشان می‌دهد). لاگ‌ها در حافظه نگه داشته می‌شوند
(پیش‌فرض ۵۰۰۰ خط، با `EXIR_PANEL_LOG_LIMIT` قابل تغییر).

> ⚠️ **امنیت**: پنل می‌تواند سفارش واقعی بفرستد و به فایل توکن دسترسی دارد. پیش‌فرض روی
> `0.0.0.0` بالا می‌آید تا از مرورگر خودتان در دسترس باشد؛ اگر لازم نیست، با
> `--host 127.0.0.1` فقط روی خود سرور بایند کنید و از تونل SSH استفاده کنید.

## لاگین
```bash
python exir_bot.py --login-only        # فقط لاگین و ذخیره‌ی توکن (مثلاً صبح قبل از بازار)
```
1. تصویر کپچا از `GET /captcha` گرفته می‌شود (کوکی `client_login_id` با اعتبار ۱۲۰ ثانیه)، در `captcha.jpg` ذخیره می‌شود، با نمایشگر سیستم باز می‌شود و **هم‌زمان در مرورگر خودتان** (لینکی که در ترمینال چاپ می‌شود) نمایش داده می‌شود.
2. نام کاربری، رمز (مخفی) و کد کپچا پرسیده و به `POST /api/v2/login` فرستاده می‌شود. کد کپچا را می‌توانید در همان صفحه‌ی مرورگر بفرستید یا در ترمینال سرور تایپ کنید.
3. توکن (`authToken` / کوکی `JWT-TOKEN`) در `.exir_token.json` ذخیره می‌شود و تا زمان انقضا (حدود ۸ ساعت) دوباره استفاده می‌شود.
4. سفارش‌ها مثل مرورگر با کوکی `JWT-TOKEN` فرستاده می‌شوند.

کپچا باید ظرف ۱۲۰ ثانیه وارد شود؛ اگر دیر شد یا ناخوانا بود، در صفحه‌ی مرورگر «🔄 کپچای جدید» را بزنید (یا در ترمینال Enter خالی).
می‌توانید به‌جای لاگین، توکن را از کوکی `JWT-TOKEN` مرورگر بردارید و با `--token` بدهید.

## کپچا در مرورگر خودتان (سرور بدون نمایشگر / VPS)
سرور معمولاً نمایشگر ندارد؛ ربات یک **وب‌سرور موقت** روی همان سرور بالا می‌آورد و لینکی در ترمینال چاپ می‌کند:

```
🌐 کپچا را در مرورگر باز کنید (یکی از این آدرس‌ها):
   http://192.168.1.50:8765/Xy7Kd2Qp1a/
   http://127.0.0.1:8765/Xy7Kd2Qp1a/
   اگر سرور از راه دور است: روی کامپیوتر خودتان اجرا کنید →  ssh -L 8765:127.0.0.1:8765 user@server
```

- لینک را در مرورگر باز کنید، کد تصویر را ببینید و **در همان صفحه** بفرستید (یا در ترمینال سرور تایپ کنید).
- هر «گرفتن کپچا»ی جدید (انقضا، درخواست شما، یا تلاش دوباره‌ی لاگین) تصویر صفحه را خودکار به‌روز می‌کند؛ نیازی به رفرش دستی نیست.
- بعد از لاگین، وب‌سرور خودش بسته می‌شود (عمر کل آن به همان ۱۲۰ ثانیه‌ی کپچا محدود است). آدرس با یک توکن تصادفی محافظت می‌شود و تصویر کش نمی‌شود.
- پیش‌فرض روشن است. برای خاموش کردن `--captcha-web off` و برای بایند فقط روی خود سرور `--captcha-web-host 127.0.0.1` را بدهید.

> ⚠️ **تصویر کپچا را در مرورگر خودتان مستقیماً از آدرس کارگزاری باز نکنید.**
> کپچای اکسیر به کوکی `client_login_id` همان نشست گره خورده است؛ اگر تصویر را مرورگر شما بگیرد، آن تصویر به نشست مرورگر شما می‌چسبد و لاگینی که از سرور فرستاده می‌شود خطای
> `HTTP 403` با `errorCode: 9009` و پیام «مشکل امنیتی.درخواست معتبر نمی باشد» می‌گیرد. به همین دلیل تصویر باید با همان session ربات گرفته شود و تنها *کد* از مرورگر شما بیاید —
> لینکی که ربات چاپ می‌کند دقیقاً همین تصویرِ گرفته‌شده با session سرور را نشان می‌دهد.

| آرگومان | توضیح | پیش‌فرض |
|---|---|---|
| `-s` | نماد / نام / تگ یا ISIN (`insMaxLcode`) | پرسیده می‌شود |
| `-q` | تعداد | پرسیده می‌شود |

## خطای ۴۰۳ (۹۰۰۹) و ۴۲۲ — چه فرقی دارند؟
| وضعیت | معنی | راه‌حل |
|---|---|---|
| `403` + `errorCode 9009` | رد امنیتی؛ علت دقیق از این کد به‌تنهایی مشخص نیست | اول `python probe_order.py --yes` را بزنید (بخش بعد)؛ اگر چیزی پیدا نشد، لاگین را روی همان سرور با `--login` انجام دهید و از کپچای `--captcha-web` استفاده کنید |
| `422` | امنیت اوکی است، ولی **بدنه‌ی سفارش** از نظر اعتبارسنجی رد شده | فیلد خطادار در پاسخ سرور (`errors`/`description`) را ببینید؛ یا با `--body-file` عیناً درخواست مرورگر را بازپخش کنید |

دلایل رایج ۴۲۲: قیمت خارج از دامنه‌ی مجاز روز/توقف یا غیرمضرب در گام قیمت، تعداد بیش از سقف حجم
هر سفارش، نماد در حال توقف، یا لحظه‌ای که امکان ثبت سفارش نیست.

### پیدا کردن علت ۹۰۰۹ با «حذف فرضیه‌ها» — `probe_order.py`
چون علت ۹۰۰۹ از خودِ این کد معلوم نمی‌شود، این ابزار هر فرضیه را **جداگانه** امتحان می‌کند:
هر «واریانت» یک تفاوت کوچک با درخواست فعلی ربات دارد (مثلاً بدون `clientid`، با
`x-app-n` به شکل مرورگر، با `Authorization` به‌جای کوکی، با `referer` صفحه‌ی ورود، …).

```bash
python probe_order.py                    # فقط فهرست واریانت‌ها — هیچ درخواستی نمی‌رود
python probe_order.py --yes              # اجرای واقعی (کمتر از ۲۰ ثانیه)
python probe_order.py --yes --app-n-candidate "2018887747744.29964494"
python probe_order.py --yes --clientid-candidate "<مقدار مرورگر>" --json probe.json
```

- 🔒 **هیچ سفارش واقعی ثبت نمی‌شود:** بدنه‌ی هر درخواست عمداً نامعتبر است (نماد ناموجود +
  تعداد ۰ + قیمت ۰)، پس حتی اگر لایه‌ی امنیت اجازه بدهد، کارگزار در مرحله‌ی اعتبارسنجی رد می‌کند.
- تفسیر نتیجه: `403/9009` یعنی «این شکل از درخواست رد شد» و `422` (یا خطای اعتبارسنجی دیگر)
  یعنی «امنیت پاس شد و درخواست به اعتبارسنجی سفارش رسید»؛ پایان کار، واریانت‌های موفق و
  پرچمِ معادل‌شان را چاپ می‌کند (مثلاً `--app-n "…"` یا `--auth-mode bearer`).
- برای مقایسه‌ی «مقدار واقعی مرورگر» با ربات، همان مقدار `x-app-n` و `clientid` را از
  DevTools کپی کنید و با `--app-n-candidate` / `--clientid-candidate` بدهید.
- فقط اگر خواستید عمداً یک سفارش *واقعی* بفرستید: `--body-file <json> --allow-real-body --only current`
  (با این پرچم، اجرای چند واریانت هم‌زمان بسته است تا چند سفارش واقعی ثبت نشود).

هنگام رد شدن درخواست، ربات خودش **درخواستی که فرستاده شد** (خط اول + هدرها + بدنه، با
مقدار کوتاه‌شده‌ی کوکی/توکن) را یک‌بار در لاگ چاپ می‌کند (`📤`). همان بلوک را با درخواست
مرورگر در DevTools مقایسه کنید؛ مقدار حساس در آن کوتاه شده و برای اشتراک‌گذاری امن است.

### بازپخش دقیق درخواست مرورگر (برای رفع ۴۲۲)
در مرورگر: `F12` ← Network ← همان درخواست `POST /api/v1/order` ← راست‌کلیک ← **Copy → Copy as fetch**،
در فایلی مثل `order.js` ذخیره کنید و اجرا کنید:
```bash
python exir_bot.py --body-file order.js --now
```
ربات بدنه را **بایت‌به‌بایت** مثل مرورگر می‌فرستد و هدرهای آن snippet (`x-app-n`، `referer`، …) را هم روی
همان نشست اعمال می‌کند؛ تعداد/قیمت/نماد از خود بدنه خوانده می‌شوند. اگر بدنه یک JSON خالص باشد
(بدون کد جاوااسکریپت) هم همان `--body-file` کار می‌کند و `--body-json '<json>'` هم معادل آن است.

> در مقایسه‌ی هدرها، تنها چیزهایی که ربات نمی‌فرستد `baggage`/`sentry-trace` (تلهمتری Sentry) و
> `sec-fetch-*` معادل‌های مرورگری هستند؛ بقیه (accept، accept-language، content-type، origin، referer،
> `sec-ch-ua*`، `sec-fetch-*`، `pragma`/`cache-control`، `user-agent`، `x-app-n`) مثل مرورگر ارسال می‌شوند.
> `x-app-n` را می‌توانید با `--app-n` بدهید — وگرنه ربات همان مقداری را که در لاگین ساخته (یا
> تولیدیِ هم‌شکل با نمونه‌ی مرورگر) در سفارش‌ها هم می‌فرستد. `clientid` هم مثل درخواست ورود
> روی همه‌ی درخواست‌ها فرستاده می‌شود (پیش‌فرض: خالی؛ با `--clientid` تغییر، با `off` حذف).

## ابزار مقایسه‌ی درخواست مرورگر با ربات
اگر مطمئن نیستید «هدر درست و کامل است یا نه»، از DevTools درخواست را کپی کنید و با این ابزار مقایسه کنید:
```bash
# هدرهای خام (DevTools → Headers → راست‌کلیک → Copy)، یا Copy as fetch، یا Copy as cURL
python compare_request.py browser.txt -s IRO7TONP0001 -q 10 -p 6700 --app-n "802547130322.33659654"
pbpaste | python compare_request.py - -q 10 -p 6700      # مستقیم از کلیپ‌بورد (macOS)
```
خروجی: کدام هدر یکسان است، کدام متفاوت، چه چیزی فقط در مرورگر است (و آیا مهم است یا تلهمتری/WAF)،
نام کوکی‌ها، و مقایسه‌ی فیلدبه‌فیلد بدنه (Payload) با بدنه‌ی ربات.

با `--emit-curl` هم یک دستور `curl` **معادلِ دقیقِ درخواست ربات** چاپ می‌شود تا بتوانید همان را در
ترمینال یا Console مرورگر خودتان اجرا کنید و ببینید کارگزار چه می‌گوید (با `--show-token` مقدار کامل توکن).

## نماد ← ISIN
- اگر ISIN (مثل `IRO7TONP0001`) بدهید مستقیم استفاده می‌شود.
- اگر نماد فارسی بدهید، اول در `symbols.json` و بعد در TSETMC جستجو و نتیجه در `symbols.json` ذخیره می‌شود.

## همگام‌سازی خودکار زمان
ربات قبل از شروع، خودش اختلاف ساعت سیستم با زمان دقیق را اندازه می‌گیرد و همه‌ی زمان‌بندی‌ها را با ساعت
تصحیح‌شده انجام می‌دهد. **نیازی به root نیست و ساعت سیستم تغییر نمی‌کند.**

- `auto` (پیش‌فرض): اول NTP (پورت UDP 123) از چند سرور به‌صورت موازی؛ نمونه با کمترین تأخیر انتخاب می‌شود (دقت چند میلی‌ثانیه).
  اگر NTP در دسترس نبود (مثلاً فیلتر یا فایروال)، با ساعت سرور کارگزاری همگام می‌شود.
- `server`: فقط ساعت سرور کارگزاری. هدر `Date` ثانیه‌ای است، ولی ربات با پیدا کردن لحظه‌ی دقیق عوض شدن ثانیه
  (حدود ۵ ثانیه، ~۲۴ درخواست سبک `HEAD`) دقت را به حدود RTT می‌رساند.
- اگر انتظار طولانی باشد، حدود ۴۵ ثانیه قبل از شروع دوباره همگام‌سازی می‌شود.
- منبع زمان، دقت و اختلاف با ساعت سیستم در خلاصه‌ی سفارش نمایش داده می‌شود.

## نکات
- کارگزار در پاسخ لاگین `sendOrderDelay: 400` برمی‌گرداند؛ اگر با ۳۰۵ms خطای محدودیت گرفتید `-i 400` را امتحان کنید.
- اگر `HTTP 403` با `errorCode: 9009` («مشکل امنیتی.درخواست معتبر نمی باشد») گرفتید، یعنی نشست/کپچا معتبر نیست:
  تصویر کپچا را در مرورگر خودتان از خود کارگزاری باز نکنید (به کوکی `client_login_id` مرورگر شما گره می‌خورد)؛ از لینک `--captcha-web` استفاده کنید.
- اگر با مرورگر هم همان سفارش `422` می‌گیرد، مشکل از ربات نیست؛ مقدار فیلدها (قیمت/تعداد) مطابق قواعد بازار نیست.
- بهتر است لاگین روی همان سروری انجام شود که سفارش‌ها را می‌فرستد (نشست ممکن است به IP گره خورده باشد)؛ اگر توکن را از کامپیوتر دیگری آورده‌اید و ۹۰۰۹ می‌گیرید، روی سرور با `--login` دوباره وارد شوید.
- `.exir_token.json` و `captcha.*` در `.gitignore` هستند؛ توکن و رمز را جایی منتشر نکنید.
- هر درخواست در یک thread جداگانه ارسال می‌شود تا کندی پاسخ‌ها فاصله‌ی ۳۰۵ms را به هم نزند.
- با پیش‌فرض، بعد از اولین پاسخ `orderSuccess` ارسال متوقف می‌شود (درخواست‌هایی که قبلاً فرستاده شده‌اند ممکن است ثبت شوند).


### ورود موفق ولی سفارش با `HTTP 403 / errorCode 9009` رد می‌شود

نمایش نام حساب پس از ورود فقط موفقیت لاگین را نشان می‌دهد؛ تضمین نمی‌کند نشست/هدرهای
درخواست سفارش پذیرفته شوند. علت دقیق ۹۰۰۹ از خود این کد معلوم نیست.

- کوکی‌های معتبر میزبان کارگزاری و دامنهٔ مادر همراه توکن ذخیره و بازیابی می‌شوند؛
  توکن‌های JWT تکراری در دامنه/مسیرهای مختلف قبل از اعمال توکن فعلی حذف می‌شوند.
- با دریافت `401` یا `403 / 9009`، ارسال درخواست‌های زمان‌بندی‌شدهٔ بعدی متوقف می‌شود،
  حتی اگر گزینهٔ توقف پس از موفقیت خاموش باشد. درخواست‌هایی که از قبل در جریان‌اند
  ممکن است هنوز پاسخ بدهند. توقف دستی یا امنیتی دیگر با پیام موفقیت گزارش نمی‌شود.
- پاسخ ریدایرکت سفارش دنبال نمی‌شود و صفحهٔ HTML به‌عنوان سفارش موفق شمرده نمی‌شود.

پس از به‌روزرسانی برنامه، دوباره از پنل لاگین کنید تا کوکی‌هایی که نسخهٔ قبلی ذخیره
نمی‌کرد بازیابی شوند. برای عیب‌یابی، در پوشهٔ برنامه اجرا کنید:

```bash
python diagnose_session.py
# اگر پنل با تنظیمات دیگری اجرا شده، همان تنظیمات را به گزارش‌گیر بدهید:
python diagnose_session.py --base-url https://khobregan.exirbroker.com --token-file .exir_token.json
```

این دستور **آفلاین است، هیچ درخواست شبکه/سفارشی نمی‌فرستد** و مقدار توکن، کوکی، رمز،
نام حساب یا مقدار هدرها را چاپ نمی‌کند. خروجی شامل نام/دامنه/مسیر کوکی‌ها، وجود هدرها و
همخوانی `x-app-n` با نشست ذخیره‌شده است. خروجی، پذیرش درخواست توسط کارگزاری را تأیید نمی‌کند.
اگر پاسخ ورود `sendOrderDelay` دارد، فاصلهٔ ارسال را کمتر از مقدار اعلام‌شده تنظیم نکنید؛
مثلاً برای `400ms`، فاصلهٔ `305ms` مناسب نیست. این تفاوت به‌تنهایی علت ۹۰۰۹ را ثابت نمی‌کند.
اگر الگوی جایگزین `NaN.<digits>` برای `x-app-n` دیده شد، توکن ذخیره‌شده از نسخهٔ قدیمی است؛
یک بار دوباره لاگین کنید تا مقدار تولیدیِ هم‌شکل با مرورگر (`<۱۳ رقم>.<۸ رقم>`) ساخته شود،
یا مقدار دقیق مرورگر را با `--app-n` بدهید. این هشدار به‌تنهایی علت قطعی خطا نیست.

برای مقایسهٔ تکمیلی، مشخصات درخواست موجود `POST /api/v1/order` در DevTools مرورگر رسمی
را بررسی کنید؛ نیازی به ثبت سفارش جدید برای جمع‌آوری اطلاعات نیست. قبل از اشتراک‌گذاری،
**مقادیر** `Cookie`، `Authorization`، JWT، رمز و اطلاعات شخصی را پاک کنید؛ نام کوکی‌ها،
آدرس/روش درخواست، نام هدرها، شکل `x-app-n` و بدنهٔ غیرحساس برای عیب‌یابی مفیدند.
